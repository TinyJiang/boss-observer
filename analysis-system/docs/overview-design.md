# 分析系统总览设计

## 1. 定位

`analysis-system/` 是独立的招聘行为分析系统，用于消费 CLS 中的 BOSS 招聘事实事件，形成后端数据链路、查询 API 和前端管理界面。

本系统参考父项目协作规范和日志契约，但不复用 Chrome 插件运行时代码。分析系统和插件之间唯一稳定共享物是父项目日志规范：

- `../../docs/modules/12-log-specification.md`

本文件只做 overview 级设计，说明产品能力、前后端模块边界、数据链路和第一版推进顺序。详细表结构、接口路径、指标 SQL、权限模型、页面交互和算法口径放到后续模块设计中展开。

## 2. 用户可见能力

### 2.1 大盘

大盘用于回答“现在有哪些人在活跃、活跃到什么程度、数据链路是否新鲜”。

第一版展示方向：

- 当前实时活跃操作员列表，包括操作员姓名、账号匹配状态、最后活跃时间和距现在几分钟。
- 当前活跃总人数，以及按最近活跃窗口分层的数量，例如刚刚活跃、几分钟内活跃、较久未活跃。
- 活跃操作员正在关联的岗位、页面类型和最近关键动作摘要，例如曝光、详情、打招呼、聊天打开。
- 数据新鲜度和健康状态，例如最近入库时间、消费延迟、解析失败数量。

说明：

- “活跃”只表示分析系统在近期事件流中观察到该操作员的事实事件，不表示 BOSS 官方在线状态。
- 活跃窗口、延迟容忍和排序规则在详细设计中定义，应支持配置。

### 2.2 单人详细数据分析

单人页用于回答“某个操作员在候选人链路上的实际行为和转化情况如何”。

第一版统计方向：

- `card` 维度：候选人列表曝光、卡片曝光、岗位分布、候选人快照分布。
- `detail` 维度：详情打开次数、详情停留时长、从卡片到详情的关联漏斗。
- 打招呼漏斗：打招呼点击、成功、失败、点击到结果耗时，以及按入口、岗位、列表页的拆分。
- 聊天指标：聊天打开、可见快照覆盖、候选人回复、招聘方回复、首响或跟进时长。
- 回复率和微信获取率：基于聊天快照和 `candidate_chat.wechat_captured` 事件生成，具体分母、去重和时间窗在详细设计中定义。
- 页面与会话：工作页面停留、路由切换、异常事件和采集健康状态。

说明：

- 聊天快照当前是 `visible_dom`，可能不完整。所有回复类指标都需要展示完整性提示，不能伪装成全量历史。
- 默认不展示聊天正文、联系方式和完整简历正文。需要正文排查时必须有单独权限和审计。

### 2.3 单人操作深度挖掘

深度挖掘用于回答“这个操作员具体采用了什么操作路径，哪些策略线索值得复盘”。

第一版探索方向：

- 招呼策略：打招呼入口、时机、详情停留后是否打招呼、不同候选人快照下的触达路径。
- 岗位策略：不同 `job_id` 下的曝光、详情、打招呼、聊天和微信获取链路。
- 筛选策略：筛选面板打开、筛选条件应用、筛选后候选人曝光与后续动作。
- 聊天策略：打开聊天后的回复节奏、候选人先发和招聘方跟进间隔、微信获取前后的事件序列。
- 异常与机会点：只展示事实线索和可解释指标，不在系统中写死员工绩效判断、候选人质量评分或话术质量结论。

## 3. 总体架构

```text
CLS 原始日志主题
  -> CLS 定时 SQL 分析
     -> 分钟级汇总日志主题 / 指标主题
     -> 汇总读取或同步
  -> Kafka 实时消费
     -> 输入消费与标准化
     -> 原始事件存储与重放
     -> 事实投影
     -> 实时活跃状态
     -> 明细查询与探索性补充
     -> 深度挖掘特征
  -> 查询 API / 导出
  -> 前端管理界面
```

第一版可以在一个 Python 应用中启动多个后端进程角色：

- `cls-consumer`: 从 CLS Kafka 协议或补数入口读取事件。
- `event-normalizer`: 把 CLS 扁平字段解析成内部事件对象。
- `raw-event-store`: 幂等保存原始事件和解析错误。
- `fact-projector`: 按事件类型写入页面、岗位、候选人曝光、详情、打招呼、聊天等事实。
- `activity-worker`: 维护操作员最后活跃时间、活跃窗口和大盘快照。
- `minute-summary-reader`: 读取 CLS 定时 SQL 写入的分钟级汇总日志主题或指标主题，作为趋势、漏斗和长周期统计的优先来源。
- `summary-sync-worker`: 必要时把 CLS 分钟汇总同步成本地缓存，用于权限过滤、跨主题组合查询和前端低延迟展示。
- `aggregate-worker`: 只做本地样本、探索性临时口径、数据质量校验和少量无法由 CLS SQL 表达的补充计算，不承担完整分钟级历史聚合。
- `log-health-probe-worker`: 基于已批准的数据链路探测日志数量、质量、新鲜度和汇总一致性，生成健康规则结果和异常事件。
- `insight-worker`: 生成面向深度挖掘的只读特征和事件序列索引。
- `api-server`: 提供前端查询、报表导出、健康检查和管理接口。

## 4. 后端模块

- 输入消费与标准化：只处理 CLS 字段解析、兼容校验和消费确认，不做业务聚合。
- 原始事件存储与重放：原样保存 `raw_events`，记录解析或投影错误，支持按条件重放。
- 事实投影：把事件转换成候选人曝光、详情、打招呼、聊天、岗位、页面会话等事实。
- 实时活跃状态：根据近期事实事件维护操作员活跃快照，为大盘提供低延迟查询。
- 分钟汇总适配：对大盘趋势、漏斗、回复时长、回复率、微信获取率等需要稳定时间序列的指标，优先读取 CLS 定时 SQL 的分钟级目标日志主题或指标主题。
- 第一批分钟汇总适配：本地系统先识别 `boss_summary_minute_prod` 中的 `boss_minute_operator_funnel` 和 `boss_minute_chat` 结果；单人漏斗和聊天指标优先使用这两类汇总，缺失时回退到 raw event/fact 临时聚合。
- 本地补充聚合：只覆盖 CLS SQL 暂时不适合表达的探索性问题、敏感权限过滤后的二次组合、以及开发环境离线样本验证。
- 日志健康度探测：判断日志数量、字段质量、解析投影质量、汇总新鲜度和链路心跳是否正常；生产环境不得把 CLS Search/SearchLog 作为探测数据源。
- 深度挖掘特征：组织候选人链路、岗位链路、筛选链路和聊天序列，服务探索分析。
- 查询 API：为前端提供稳定查询边界，默认隐藏敏感正文，所有管理操作可审计。
- 运行安全：管理配置、凭据、部署、监控、导出和敏感数据访问边界。

后端不向插件下发业务判断、采集策略或候选人评分，也不把分析结论回写为事实事件。

## 5. 前端模块

前端是分析系统的管理界面，只通过后端 API 读取数据，不直接访问数据库、CLS、Chrome 插件或 BOSS 页面。

第一版模块划分：

- 应用外壳：登录状态、权限、全局日期范围、操作员筛选、岗位筛选和数据新鲜度提示。
- 大盘页：实时活跃人数、活跃操作员列表、最近关键动作、岗位和页面分布、数据健康提示。
- 操作员详情页：单人 `card -> detail -> greeting -> chat -> wechat` 漏斗、时间趋势和维度拆分。
- 深度挖掘页：按操作员查看候选人链路、岗位链路、筛选链路和聊天节奏，不默认暴露敏感正文。
- 数据质量页：日志数量健康、字段质量、解析失败、未知事件类型、汇总新鲜度、消费延迟、重放任务和导出任务状态。

前端展示应明确区分事实、统计指标和探索性线索。涉及回复率、微信获取率、策略线索等派生结果时，需要展示口径说明入口和数据完整性提示。

本地开发阶段操作员列表可从 `config/operators.local.json` 热加载，用于配置展示名称、BOSS 账号名和启用状态；该文件只影响展示，不作为事实来源。正式部署阶段应迁到数据库或后台管理页。

## 6. 数据主题

| 数据主题 | 主要事件来源 | 支撑能力 |
| --- | --- | --- |
| 页面与活跃 | `page_session.*`、其他操作事件的 `occurred_at` | 大盘活跃人数、最后活跃时间、页面停留 |
| 岗位上下文 | `job_context.*`、`context.jobContext` | 岗位维度分析、岗位策略挖掘 |
| 候选人卡片 | `candidate_list.list_viewed`、`candidate_list.card_exposed` | 曝光统计、卡片到详情漏斗 |
| 候选人详情 | `candidate_detail.opened`、`candidate_detail.closed` | 详情打开、停留时长、详情到打招呼路径 |
| 打招呼 | `candidate_greeting.clicked`、`succeeded`、`failed` | 打招呼漏斗、入口拆分、结果耗时 |
| 聊天 | `candidate_chat.opened`、`snapshot_captured`、`report_required`、`capture_failed` | 回复节奏、回复率、聊天补采健康 |
| 微信 | `candidate_chat.wechat_captured` | 微信获取率、微信获取链路 |
| 筛选 | `candidate_filter.panel_opened`、`candidate_filter.applied` | 筛选策略复盘、筛选后链路分析 |
| 运行健康 | `queue.*`、`upload.*` 预留事件、解析和消费状态 | 数据可信度、监控告警 |
| 日志健康 | `raw_events`、错误表、分钟汇总、日级汇总、`boss_10min_log_quality` | 日志数量/质量探测、异常定位、健康告警 |

## 7. 数据处理原则

- 先落 `raw_events`，再解析和投影事实。
- `event_id` 是第一幂等键；缺失时进入错误记录，不猜测替代主键。
- `payload_json`、`context_json` 必须保留原文；解析失败也不能丢事件。
- 未知 `event_type` 原样保存，等待后续 parser 升级重放。
- 同一候选人的跨页面合并必须保守，低置信身份不能强合并。
- 实时大盘优先使用最近已入库或已投影事件，并展示数据新鲜度。
- 分钟级统计的权威计算尽量放在 CLS 定时 SQL。大盘趋势、操作员分钟漏斗、岗位分钟趋势、聊天回复时长分布、回复率和微信获取率都应先评估是否能由 CLS 直接预聚合。
- `boss_minute_operator_funnel` 和 `boss_minute_chat` 是第一批核心分钟任务。analysis-system 读取它们时必须把 `<missing>` operator 保留为健康异常，而不是静默归并到真实操作员。
- analysis-system 不应在本地请求链路或普通后台任务中长期重复扫描原始日志来重建分钟级数仓；本地只保留重放、抽样校验、权限过滤和探索性补充。
- 日志健康度探测必须区分“没有活动事实”和“日志链路异常”。缺少工作时段或期望流配置时，长时间无日志应返回 `unknown` 或 `warning`，不能直接解释为操作员未工作。
- CLS 定时 SQL 结果不是 PostgreSQL 表。需要复杂关系查询、权限过滤或跨主题联查时，可由 analysis-system 同步分钟汇总结果入库作为缓存，但缓存不应成为原始日志聚合的主实现。
- 所有展示层默认隐藏敏感正文，只有明确授权的后台能力才允许查看最小必要内容。

## 9. 第一版实现顺序

1. 明确大盘、单人分析和深度挖掘的第一版指标口径清单。
2. 建立配置读取、内部事件模型和 normalizer 单元测试。
3. 建立 `raw_events`、解析错误、投影错误和重放入口。
4. 实现页面、岗位、候选人曝光、详情、打招呼和聊天事实投影。
5. 优先设计 CLS 分钟级定时 SQL 任务和目标汇总主题/指标主题，例如操作员分钟活跃、分钟漏斗、岗位分钟趋势、聊天回复时长分布、微信获取分钟计数和数据健康分钟计数。
6. 接入第一批 CLS 分钟汇总读取：`boss_minute_operator_funnel`、`boss_minute_chat`，并在 API/前端展示汇总来源、最新分钟和缺 operator 异常。
7. 实现实时活跃状态和大盘查询 API。
8. 实现单人漏斗、聊天回复、微信获取等查询 API，优先读取 CLS 分钟汇总；本地只做去重候选人口径、权限过滤和临时探索补充。
9. 实现日志健康度探测模块，先覆盖 raw/summary 新鲜度、缺 operator、解析失败、未知事件和汇总延迟，再接入 `boss_10min_log_quality` 10 分钟质量汇总。
10. 实现前端大盘页、操作员详情页、深度挖掘页和数据质量页的最小闭环。
11. 接入 CLS Kafka consumer，并在真实云资源操作前记录风险和确认项。

## 10. 后续详细设计待定项

- 活跃窗口、活跃分层和最后活跃时间的精确口径。
- `card -> detail -> greeting -> chat -> wechat` 漏斗的去重、分母和跨事件关联规则。
- 聊天回复率、首响时长、跟进时长的消息配对规则和快照完整性提示。
- 微信获取率的分母选择，例如按打招呼成功、聊天打开或有效会话计算。
- 哪些分钟级指标可直接由 CLS 定时 SQL 生成，哪些必须由本系统基于事实表做二次计算。
- CLS 定时 SQL 目标主题/指标主题的命名、保留周期、读取方式、同步策略、延迟容忍和失败补偿。
- 日志健康度探测的默认阈值、工作时段配置、基线观察期和告警出口。
- 深度挖掘页的策略线索输出方式，避免变成不可解释的绩效结论。
- 敏感正文查看、导出和审计权限。
- 前端框架、路由、状态管理、图表库和设计系统。

## 11. 验证要求

- 文档变更：检查链接、模块边界和日志契约引用是否一致。
- 解析逻辑：使用 `tests/fixtures/` 中的离线 CLS 样本。
- 存储逻辑：优先用临时 PostgreSQL 或 repository fake 覆盖幂等、错误保留和重放。
- 聚合逻辑：覆盖重复事件、迟到事件、空数据、低置信候选人身份和敏感字段默认隐藏。
- 云资源：只有在任务说明清楚资源、权限和风险，并得到用户确认后执行。
