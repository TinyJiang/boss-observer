# 日常分析人员辅导看板设计

- 日期：2026-06-16
- 状态：设计确认
- 范围：`/daily-analysis` 前端信息架构、首屏内容层级、文案边界

## 目标

把当前按数据板块平铺的日常分析页，重组为面向管理者早会和团队 coaching 的人员辅导看板。

页面默认进入团队/全部操作员视角。首屏优先回答：

- 今天整体是否正常。
- 哪些辅导主题需要关注。
- 哪些操作员建议复盘。
- 今天可以给出哪些战术建议。

页面可以把操作员当销售代表看待，但表达必须保持中性，避免变成绩效排名或惩罚性判断。

## 非目标

- 不输出员工绩效结论。
- 不输出候选人质量评分。
- 不把操作员按好坏、优秀/落后、达标/不达标排序。
- 不把模型归因固化成本地规则。
- 不改变后端 `/api/daily-analysis` 数据契约，除非实现阶段发现现有字段无法支撑首屏状态。
- 不恢复主菜单入口；页面仍通过隐藏路径 `/daily-analysis` 内部访问。

## 首屏结构

首屏按从上到下的阅读路径组织。

### 1. 筛选与整体数据概览

顶部保留紧凑筛选行：

- 分析日期。
- 操作员筛选，默认全部操作员。
- 查询按钮和加载状态。

筛选行下方用很小篇幅展示整体数据概览。它不成为主内容，只提供页面上下文，建议占一行或一个低高度横条。

整体概览字段优先使用现有 payload 可得信息：

- 分析日期。
- 覆盖操作员数。
- 证据数量。
- 关键漏斗总量，例如查看、发起聊天、沟通、简历/微信/面试，按现有官方结果和行为证据可用字段展示。
- 模型生成时间或分析包更新时间。

如果字段缺失，应显示 `暂无` 或 `未覆盖`，不能用 0 伪装完整数据。

### 2. 采集异常与数据质量提示

采集异常必须出现在首屏，不放到页面底部。

展示规则：

- 没有异常时，占用很小状态位，例如 `采集状态：正常`。
- 有异常时，用紧凑告警条展示，位置在整体概览之后、辅导结论之前。
- 告警内容只说明事实和影响范围，例如“2 个岗位缺少行为证据”“1 位操作员官方结果未匹配”“聊天快照样本偏低”。
- 告警不能解释为操作员问题，也不能把采集缺口归咎于个人。

异常来源优先映射：

- `data_quality.missing_fields`
- `data_quality.unmatched_jobs`
- `data_quality.low_sample_warnings`
- `errors`
- `status = partial | failed | analyzing`
- 后续如接入日志健康结果，可合并为首屏采集状态。

### 3. 今日团队判断

这是首屏主标题区，不做大 hero，只做紧凑结论面板。

内容包括：

- 一句话整体判断：来自 `model_analysis.summary` 或后续团队级模型总结。
- 状态标签：可用、部分可用、分析中、失败。
- 结论边界提示：当数据不完整时，明确写“基于当前可用证据”。

推荐文案示例：

- “整体触达链路可用，但详情后沟通转化有 3 个辅导机会。”
- “官方结果已同步，行为证据部分缺失，今天先按可用数据做复盘。”

避免文案：

- “团队表现差。”
- “某某操作员不达标。”
- “原因确定是个人执行问题。”

### 4. 今日复盘对象

今日团队判断下方只保留一个人员列表，不再把辅导重点、复盘对象和战术建议拆成三个首屏板块。

列表按问题严重程度排序。这里的排序含义是“今天最值得优先复盘的可行动问题”，不是绩效排名、好坏排名或处罚依据。

每个操作员行包含：

- 操作员展示名。
- 严重程度或复盘优先级标签。
- 复盘重点。
- 数据波动，例如关键指标相对昨日、上周同日、7 日均值或 14 日均值的变化。
- 优化建议。
- 数据可信度或缺口提示。

文案使用：

- `今日复盘对象`
- `建议复盘`
- `复盘重点`
- `数据波动`
- `优化建议`
- `待确认原因`

避免使用：

- `落后`
- `低效`
- `不合格`
- `倒数`
- `责任人`
- `处罚`

优化建议必须可执行，避免空泛结论。

示例：

- “复盘详情后未打招呼的岗位，先确认候选人匹配度是否足够。”
- “检查昨日已有沟通但未推进微信的会话，优先补跟进高意向候选人。”
- “对低样本操作员先补采或延后判断，不进入早会比较。”

### 5. 个人详情分析

个人详情分析通过右侧划出抽屉展示，不再默认占用复盘对象列表下方空间。

默认规则：

- 抽屉默认收起，首屏优先保留整体概览、采集状态、今日团队判断和今日复盘对象列表。
- 点击复盘对象列表中的“查看详情”打开右侧抽屉，并切换当前个人详情。
- 抽屉打开时可以压缩左侧复盘对象列表区域；关闭后列表恢复完整宽度。
- 窄屏下抽屉改为列表下方展开，避免横向溢出。
- 如果筛选了操作员，抽屉打开时优先展示该操作员。
- 如果没有筛选操作员，抽屉打开时默认展示今日复盘对象列表中优先级最高的人。

个人详情分析只展示管理者复盘需要的核心内容，不恢复底部数据证明区。

页面结构：

- 核心数据：查看、发起聊天、沟通、收获简历、电话微信、接受面试，以及关键转化率。
- 波动归因：按个人指标相对昨日、上周同日、7 日均值和 14 日均值的偏离排序，表达为“可能归因/待确认原因”。
- 问题排查：围绕详情后触达、聊天推进、简历承接、样本完整度和岗位匹配给出检查项。
- 辅导建议：把排查项转为可执行的复盘动作。

## 页面边界

首屏之后不保留“数据证明”区。

删除以下页面板块：

- 漏斗证明。
- 辅导分析。
- 证据包。

后端 payload 仍可保留 `volatility_metrics` 和 `evidence_bundle`，用于模型输入、调试或后续单独页面；本页面不再展示这些底部证明内容。

## 组件调整建议

基于现有 React 结构，优先重组 `DailyAnalysisTab`，不要扩大前端架构。

建议新增或拆分以下展示组件：

- `DailyOverviewStrip`：筛选下方的小型整体数据概览。
- `DailyCollectionAlert`：首屏采集异常和数据质量提示。
- `DailyCoachingSummary`：今日团队判断。
- `DailyReviewOperatorList`：今日复盘对象，按问题严重程度排序，展示操作员数据波动和优化建议。
- `DailyPersonalDetailDrawer`：个人详情右侧抽屉，打开时压缩复盘对象列表区域，提供关闭入口。
- `DailyPersonalDetailPanel`：个人详情分析，展示核心数据、波动归因、问题排查和辅导建议。

现有组件可复用：

- `DailyStatusBadge`

## 状态处理

加载状态必须可见：

- 首次加载：首屏显示分析包加载中。
- 刷新中：保留旧结果，并显示刷新状态。
- 部分可用：首屏继续展示结论，但在采集异常条中标明缺口。
- 失败：首屏展示失败原因和可重试入口，不展示过期结论为当前结论。

异常优先级：

1. `failed` 或 `errors`：首屏错误条。
2. `partial`：首屏告警条。
3. 低样本/缺字段/未匹配岗位：首屏数据质量提示。
4. 无异常：紧凑正常状态。

## 文案原则

页面的语气是“管理者辅导团队”，不是“系统评价员工”。

使用：

- 复盘
- 辅导
- 机会缺口
- 待确认
- 建议动作
- 数据证据
- 当前样本

避免：

- 绩效
- 排名
- 差
- 落后
- 不合格
- 责任
- 偷懒
- 扣分

当模型输出含有过强评价时，前端展示层应优先以中性标题包裹；后续模型 prompt 也应约束为辅导语言。

## 验证要求

实现阶段至少验证：

- `/daily-analysis` 仍可通过隐藏路径访问。
- 首屏在桌面宽度下优先看到：整体概览、采集状态、团队判断和今日复盘对象列表。
- 有 `data_quality` 或 `errors` 时，异常出现在首屏。
- 操作员列表不使用绩效排名、落后、差等词。
- 个人详情分析通过右侧抽屉打开；打开时列表区域被压缩，关闭后恢复。
- 个人详情分析包含核心数据、波动归因、问题排查和辅导建议。
- 不渲染“数据证明”“漏斗证明”“辅导分析”或“证据包”板块。
- `cd frontend && npm run build` 通过。
- 相关 React 静态测试或前端结构测试更新。

## 第一版完成标准

第一版完成后，管理者打开 `/daily-analysis`，应先看到一个克制的团队辅导摘要，而不是数据表墙。

页面应能在首屏完成以下判断：

- 今天整体数据是否可用。
- 有没有采集异常影响判断。
- 哪些操作员建议复盘，分别看到了什么数据波动。
- 每个复盘对象的优化建议是什么。
- 当前个人的核心数据、可能波动原因、排查入口和辅导建议是什么。
