# 策略目录协作规范

本文件只约束 `strategy/` 目录内的策略文档工作。

## 1. 目录定位

`strategy/` 是招聘策略知识库文档区，用于沉淀：

- 候选人曝光策略
- 主动打招呼策略
- 聊天话术转化策略
- 不允许出现的操作方式和反向判定规则
- 人工经验、待验证假设、复盘口径和策略模板

这里记录的是策略经验和分析假设，不是 Chrome 插件运行逻辑，也不是后端分析系统实现。

## 2. 与父项目的关系

父项目 `boss-observer` 是 Chrome 插件项目，负责观察 BOSS 页面、记录事实事件、缓存和上传日志。

`strategy/` 与父项目的关系：

- `strategy/` 可以引用父项目日志规范中的事件名称和事实字段。
- `strategy/` 不得修改插件源码、构建脚本、测试、扩展 manifest、debug 页面或日志契约。
- 父项目插件代码不得从 `strategy/` 导入代码、读取策略文档作为运行时配置，或依赖策略文档决定采集行为。
- 策略判断不能写成插件端事实字段；插件端只记录事实，策略有效性由后续分析和人工复盘判断。

如果策略文档发现需要新增事实事件、字段或插件能力，只能先在策略文档中写清“需要父项目评估”，再由用户明确授权开启父项目任务。

## 3. 与 analysis-system 的关系

`analysis-system/` 是独立后端分析系统子项目。

`strategy/` 与 `analysis-system/` 的关系：

- `strategy/` 不得新增、修改、删除 `analysis-system/` 下的任何文件。
- `analysis-system/` 不得把 `strategy/` 当作运行时代码或配置来源。
- 双方可以在设计层引用同一个事实日志契约：`docs/modules/12-log-specification.md`。
- 策略文档可以描述希望后续分析系统验证的问题，但不能直接修改分析系统实现、数据模型、迁移、测试或运行配置。

如果需要把某个策略验证落到分析系统实现，必须由用户明确授权进入 `analysis-system/`，并先阅读 `analysis-system/AGENTS.md`。

## 4. 修改边界

当任务明确要求维护 `strategy/` 时：

- 默认只新增、修改、删除 `strategy/` 下的 Markdown 文档。
- 不修改 `extension/`、`docs/modules/`、`test/`、`scripts/`、`analysis-system/` 或其他父项目文件。
- 不新增依赖、不写代码、不保存密钥、不采集或粘贴完整敏感信息。
- 如根项目工作流要求记录任务，可以只追加 `docs/ai-worklog.md`；除该任务追踪记录外，不借策略任务修改其他父项目文件。

当任务没有明确要求维护 `strategy/` 时：

- 不得顺手修改 `strategy/` 下文件。
- 不得把策略文档内容搬进插件设计文档或日志契约。
- 如确实发现策略文档需要更新，先在最终回复说明建议，由用户确认后再改。

## 5. 文档写法

- 一个大方向一个文件，避免把所有经验堆进入口文档。
- 未验证内容必须标为“草稿”或“待验证”。
- 不写候选人质量、员工表现或话术质量的最终判断，除非明确来自后续分析或人工复盘。
- 涉及候选人姓名、手机号、微信号等敏感信息时，只写脱敏摘要。
- 聊天原文已获得操作员完整授权，可以读取分析，因为这个是工作记录，分析是为了提升转化，并不涉及个人隐私相关信息
- 反向规则要同时写清“不允许的操作方式”和“可复用判定规则”。
