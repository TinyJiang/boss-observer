# BOSS 招聘行为日志系统概要设计

## 1. 项目定位

本项目是一个用于 BOSS 直聘招聘场景的行为日志采集系统。

系统通过 Chrome 插件记录招聘专员在 BOSS 直聘上的核心操作，并将日志上报到成熟日志系统。后续可以基于导出的日志，使用 AI 或独立分析系统总结有效策略、监督员工工作、分析回复速度和聊天质量。

第一阶段重点是把日志采集链路打通，保证关键行为能被稳定记录、可靠上报、方便导出。

## 2. 核心目标

### 2.1 记录招聘行为

完整记录招聘专员在 BOSS 直聘上的关键操作，尤其是候选人筛选链路：

- 候选人列表曝光
- 候选人详情打开或曝光
- 候选人被打招呼

这三类日志是 MVP 的最高优先级，用来支撑后续分析招聘专员的候选人筛选能力。

### 2.2 沉淀有效策略

通过大量行为日志，后续分析哪些筛选方式、候选人选择方式、打招呼方式、聊天节奏和话术更容易带来回复、持续沟通和转化。

### 2.3 监督员工工作

通过行为日志判断招聘专员是否真实、持续、有效地工作。

重点关注：

- 是否浏览候选人
- 是否打开候选人详情
- 是否主动打招呼
- 是否及时回复候选人
- 是否存在长期无操作
- 是否存在低质量批量操作

### 2.4 支持回复速度和聊天质量分析

回复速度和聊天质量是后续分析的重要目标。

聊天记录采集需要单独研究。原因是招聘专员可能同时通过电脑端和手机端与候选人沟通，Chrome 插件只能稳定观察电脑端 BOSS 页面，无法完整覆盖手机端产生的消息。

当前采用“打开聊天窗口触发文本快照 + 插件 popup 统计今日未上报聊天”的方式记录聊天。手机端消息如果同步到电脑端聊天列表，插件只在自身 popup 中列出对应会话供招聘专员打开补采，不自动代替员工操作，也不向 BOSS 页面插入提示 DOM。

## 3. 设计原则

### 3.1 插件只记录事实

Chrome 插件只负责观察、记录、上传。

每条日志都是独立事实事件，不要求插件在本地建立事件依赖关系。

例如：

- 候选人 A 列表曝光
- 候选人 A 详情打开
- 候选人 A 被打招呼
- 候选人 A 发来消息
- 招聘专员回复候选人 A

后续分析系统可以基于这些独立事件计算漏斗、判断策略、识别异常。

### 3.2 对接成熟日志系统

第一阶段优先对接腾讯云 CLS 作为成熟日志系统。

Chrome 插件负责生成事实日志并上报，日志系统负责接收、保存、查询和导出。

### 3.3 日志细节后置设计

本文档只明确系统模块、模块职责和模块下需要记录的日志类型。

日志字段、候选人标识方式、DOM 选择器、页面识别方式、上传结构等详细内容，在后续真机跑 BOSS 直聘页面时再设计。

## 4. 总体架构

```text
招聘专员操作 BOSS 直聘
        ↓
Chrome 插件观察页面行为
        ↓
插件生成独立事实日志
        ↓
插件本地缓存
        ↓
插件批量上传
        ↓
成熟日志系统接收并保存日志
        ↓
按日期、员工、岗位、事件类型导出
        ↓
后续 AI 或分析系统处理
```

### 5.1 Chrome 插件模块

Chrome 插件是日志采集端，只在 BOSS 直聘相关页面运行。

采集前置门禁：

- 插件 popup 必须配置操作员 ID 和账号姓名。
- content script 会识别 BOSS 页面展示的账号姓名，background 在入队前统一校验配置姓名与页面姓名是否一致。
- 未配置、未检测到页面姓名或姓名不一致时，插件在 popup 给出严重提示，并禁止正式事件写入本地队列和上传。
- 通过校验的每条事件都会带上操作员信息，供日志系统按招聘专员维度检索。

#### 5.1.1 页面会话模块

用于记录招聘专员是否进入工作场景，以及页面使用过程。

需要记录的日志：

- 插件启动日志
- 进入 BOSS 页面日志
- 离开 BOSS 页面日志
- 页面切换日志
- 页面停留日志
- 插件异常日志

#### 5.1.2 职位模块

用于记录招聘专员当前在哪个招聘职位下操作。

需要记录的日志：

- 当前职位识别日志
- 职位切换日志
- 职位页面曝光日志
- 职位上下文变化日志

职位信息主要作为后续分析候选人行为时的上下文。

#### 5.1.3 筛选模块

用于记录招聘专员如何使用筛选条件。

需要记录的日志：

- 筛选面板打开日志
- 筛选确认日志

筛选日志用于后续分析不同筛选策略对候选人打开率、打招呼率、回复率的影响。

#### 5.1.4 候选人列表模块

用于记录招聘专员在列表里实际滚动看到过哪些候选人。

需要记录的日志：

- 候选人列表曝光日志
- 候选人卡片曝光日志

其中“候选人卡片曝光日志”是核心日志。只要候选人在列表中出现过，就应该被记录下来。

#### 5.1.5 候选人详情模块

用于记录招聘专员打开了哪些候选人的详情。

需要记录的日志：

- 候选人详情打开日志
- 候选人详情关闭日志
- 候选人详情打开日志中的牛人分析可见标记

#### 5.1.6 打招呼模块

用于记录招聘专员对哪些候选人发起了打招呼行为。

需要记录的日志：

- 打招呼按钮点击日志
- 打招呼成功日志
- 打招呼失败日志

#### 5.1.7 聊天记录模块

用于支持后续回复速度、聊天质量和话术转化率分析。

- 打开候选人聊天窗口时采集已渲染文本快照并立即尝试上传
- 服务器确认上传成功后，本地记录候选人的最后有效上报水位
- 聊天列表发现今天最近消息晚于水位时，只在插件 popup 的生产统计中列出未上报聊天
- 已换微信且页面可见微信账号时，上报微信信息用于后续追踪

#### 5.1.8 本地队列与上传模块

用于保证日志可靠上传，避免网络波动导致日志丢失。

需要维护的状态：

- 本地队列长度和待上传事件
- 最近一次上传成功时间和上传结果
- 最近一次上传失败时间和失败原因
- 事件上传成功、失败和待上传状态
- 本地队列容量与丢弃风险

当前正式业务事件仍先写入本地队列，再按批量或即时策略上传。上传链路状态进入 debug/profile 和 popup 生产统计；`upload.*`、`queue.write_failed` 等正式事件类型已预留，但当前不作为业务事件流主动上报。

### 5.2 日志系统对接模块

用于将 Chrome 插件采集到的日志上报到成熟日志系统。

需要支持的能力：

- 接收插件批量上传日志
- 保存原始事实日志
- 支持按日期查询
- 支持按招聘专员查询
- 支持按岗位查询
- 支持按事件类型查询
- 支持日志导出

### 5.3 后续分析消费模块

用于消费日志系统导出的数据，支撑策略分析和员工监督。

主要分析方向：

- 曝光到打开详情漏斗
- 打开详情到打招呼漏斗
- 打招呼到候选人回复漏斗
- 候选人筛选能力
- 招聘专员工作量
- 招聘专员工作质量
- 回复速度
- 聊天质量
- 话术转化率
- 筛选策略有效性
- 批量低质量操作

## 6. MVP 范围

MVP 先完成 Chrome 插件采集和日志系统对接。

### 6.1 Chrome 插件 MVP

需要完成：

- 只在 BOSS 直聘相关页面运行
- 支持 popup 配置操作员 ID 和账号姓名，并在采集前校验 BOSS 页面账号姓名
- 记录页面会话日志
- 记录当前职位上下文
- 记录筛选面板打开日志
- 记录筛选确认日志
- 记录候选人列表曝光日志
- 记录候选人卡片曝光日志
- 记录候选人详情打开日志
- 记录候选人详情关闭日志
- 在候选人详情打开日志中记录牛人分析可见标记
- 记录打招呼按钮点击日志
- 记录打招呼成功日志
- 记录打招呼失败日志
- 支持本地日志缓存
- 支持日志批量上传
- 支持上传失败重试

### 6.2 日志系统对接 MVP

需要完成：

- 插件日志可以上报到日志系统
- 日志系统可以保存原始日志
- 日志系统可以按日期、招聘专员、岗位、事件类型查询
- 日志系统可以导出数据供后续 AI 或分析系统使用

### 6.3 聊天记录验证 MVP

需要完成：

- 真机验证电脑端聊天页面能观察到哪些信息
- 真机验证聊天列表和聊天详情是否适合做会话快照
- 评估手机端消息对回复速度分析的影响
- 实现打开聊天窗口触发文本快照、上传成功水位和今日未上报聊天统计
- 验证已交换微信信息在真实页面中的展示和采集方式

## 7. MVP 成功标准

第一阶段完成后，系统应满足：

- 能稳定记录候选人列表中曝光过哪些候选人
- 能稳定记录招聘专员打开过哪些候选人详情
- 能稳定记录招聘专员对哪些候选人打过招呼
- 能记录职位和筛选上下文
- 能把日志可靠上传到日志系统
- 日志系统能保存原始日志
- 日志系统能按日期、员工、岗位、事件类型导出日志
- 能在聊天窗口打开时采集已渲染文本快照，并对今天有新消息但未成功上报的会话提示补采
