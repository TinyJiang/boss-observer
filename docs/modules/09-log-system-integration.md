# 日志系统对接模块详细设计

## 1. 模块定位

日志系统对接模块用于将 Chrome 插件采集到的日志上报到成熟日志系统。

本项目第一阶段不单独建设复杂后端日志服务，优先复用腾讯云 CLS 的接收、保存、查询和导出能力。

日志字段和枚举的具体契约见 [日志规范与后端分析契约](12-log-specification.md)。

## 2. 核心目标

- 接收 Chrome 插件批量上传的日志。
- 保存原始事实日志。
- 支持后续按日期、招聘专员、岗位、事件类型查询。
- 支持导出数据给 AI 或独立分析系统。
- 保留足够原始信息，避免过早加工导致后续分析受限。

## 3. 接入边界

Chrome 插件负责：

- 生成事实日志。
- 本地缓存日志。
- 批量上传日志。
- 记录上传成功、失败和重试。

日志系统负责：

- 接收日志。
- 保存日志。
- 查询日志。
- 导出日志。
- 提供基础检索能力。

## 4. 日志分类

日志系统需要接收以下类型的日志：

- 页面会话日志
- 职位日志
- 筛选日志
- 候选人列表日志
- 候选人详情日志
- 打招呼日志
- 聊天记录日志或聊天快照日志
- 本地队列与上传链路日志
- 插件异常日志

## 5. 查询维度

日志系统需要支持以下查询维度：

- 日期
- 招聘专员
- 岗位
- 候选人
- 事件类型
- 页面类型
- 上传批次
- 插件版本

具体索引和字段设计依赖选型后的日志系统能力。

## 6. 导出方向

导出的数据主要服务于后续分析：

- 招聘行为漏斗分析
- 候选人筛选能力分析
- 员工工作监督
- 回复速度分析
- 聊天质量分析
- 话术转化率分析

导出格式优先考虑日志系统原生支持的 JSON 或 CSV。

## 7. MVP 范围

MVP 需要完成：

- 插件日志可以成功上报到日志系统。
- 日志系统能保存原始日志。
- 能按日期查询日志。
- 能按招聘专员查询日志。
- 能按岗位查询日志。
- 能按事件类型查询日志。
- 能导出日志。

## 8. 真机验证点

- 选定日志系统的写入限制。
- 单次批量上传大小限制。
- 查询和导出能力是否满足分析需求。
- 是否支持去重或需要分析侧自行去重。
- 日志保留周期。
- 敏感数据存储和访问控制能力。

## 9. 腾讯云 CLS 选型说明

腾讯云 CLS（Cloud Log Service）适合作为本项目的后端日志服务，因为它原生支持日志集、日志主题、索引、检索、消费和仪表盘。

当前选定方案是插件端直传 CLS，减少自建后端复杂度。

接入时建议遵守以下约定：

- 一个业务环境一个日志集或至少一个独立日志主题。
- 我们的业务日志按“事实事件”写入 CLS，不在插件侧做分析加工。
- 插件侧仍然保留本地队列，用于失败重试和离线缓冲。
- 上传链路优先使用 CLS 匿名上传能力，通过 HTTPS 直传到日志主题。
- 开发阶段默认关闭上传，使用 `uploadEnabled` 开关控制是否真正 flush 到 CLS。
- 写入 CLS 时使用结构化日志，不要把所有字段挤成不可检索的大字符串。
- 当前本地保留的 CLS 目标地域是 `ap-shanghai`，topic id 是 `5407c0a7-3e37-4c45-a204-bf5d40f157a1`。
- `event.type`、`page_type`、`session_id`、`plugin_version`、`source_tab_id` 等字段应建立索引。
- 原始 `payload` 和 `context` 可以保留为 JSON 字符串备份，但不要依赖嵌套对象做 CLS 索引。

如果后续发现匿名直传的数据污染风险不可接受，再退回“插件本地队列 -> 自建接收服务 -> CLS”的代理方案。
