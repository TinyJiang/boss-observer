# 本地队列与上传模块详细设计

## 1. 模块定位

本地队列与上传模块用于保证 Chrome 插件采集到的日志可靠进入日志系统。

BOSS 页面操作发生在浏览器中，网络、页面刷新、标签页关闭、日志系统不可用等情况都可能导致日志丢失。该模块负责本地缓存、批量/即时上传、失败重试和上传状态记录。

## 2. 核心目标

- 所有业务日志先写入本地队列。
- 支持批量上传到日志系统，并让关键事件尽快 flush。
- 上传失败时保留日志并重试。
- 在 debug/profile 和 popup 生产统计中记录上传链路状态，便于排查日志缺失。
- 控制本地队列容量，避免影响浏览器性能。

## 3. 需要维护的状态

### 3.1 本地队列状态

记录业务日志是否进入本地队列、当前队列长度和待上传事件。

用于排查日志是否在插件端成功生成。

### 3.2 上传成功状态

记录最近一次上传成功时间、目标类型、HTTP 状态、requestId 和批次大小。

### 3.3 上传失败状态

记录最近一次上传失败时间、失败原因、批次大小和重试计数更新是否失败。

### 3.4 生产统计状态

按模块维护 produced/uploaded/failed/pending 事件状态，用于 popup 显示绿色/红色健康状态。这里统计的是事实事件数，不是业务动作数；例如一次成功打招呼通常会产生点击和成功两条事件。

### 3.5 运行链路状态

本地队列写入、上传开始、上传成功和上传失败不作为正式业务事件流主动上报；上传和队列状态以 debug/profile、popup 生产统计和控制台诊断为准。

## 4. 工作流程

```text
业务模块生成日志
        ↓
写入本地队列
        ↓
达到上传条件
        ↓
批量读取待上传日志
        ↓
上传到日志系统
        ↓
成功后标记已上传或删除
        ↓
失败后保留并等待重试
```

## 5. 上传触发条件

上传可以由多种条件触发：

- 队列达到一定数量。
- 距离上次上传达到一定时间。当前后台 alarm 至少 1 分钟触发一次，配置中的 `flushIntervalMs` 低于 1 分钟时会受 Chrome alarm 限制。
- 关键事件入队后立即 flush，包括 `candidate_detail.opened`、`candidate_detail.closed`、`candidate_greeting.clicked`、`candidate_greeting.succeeded`、`candidate_greeting.failed`、`candidate_chat.snapshot_captured`、`candidate_chat.wechat_captured`。
- 页面即将关闭或刷新。
- 网络恢复。
- 插件收到手动刷新或调试指令。

即时 flush 只影响上传时机，不绕过本地队列；事件仍然先落队列，上传成功后再从队列删除。被动或高频事件继续按批量阈值和 alarm flush。

## 6. 可靠性要求

- 日志生成后应优先落本地队列。
- 上传失败不应影响页面正常使用。
- 重试应避免过于频繁。
- 队列容量达到上限时应有明确丢弃策略和告警状态。
- 上传过程应支持幂等或允许日志系统去重。

## 7. MVP 范围

MVP 需要完成：

- 本地日志缓存。
- 批量上传和关键事件即时 flush。
- 上传成功确认。
- 上传失败重试。
- 队列容量保护。
- 上传链路状态记录到 debug/profile 和 popup 生产统计。

## 8. 真机验证点

- 浏览器插件可用的本地存储容量。
- 页面刷新、关闭时日志是否容易丢失。
- 日志系统上传接口是否支持批量。
- 上传接口失败时的错误形态。
- 长时间离线后队列是否可控。
