# 聊天记录模块详细设计

## 1. 模块定位

聊天记录模块用于支持后续回复速度、聊天质量、话术转化率和微信后续追踪分析。

该模块只记录 BOSS 页面上可观察到的事实：聊天窗口打开、当前聊天窗口已渲染的文本消息快照、以及已交换微信的可见微信信息。插件不判断聊天质量，不评价候选人，不替招聘专员操作。

## 2. 核心目标

- 招聘专员点开某个候选人聊天窗口时，采集该窗口当前可见或已加载的聊天文本快照。
- 在服务器确认上传成功后，本地记录该候选人的最后有效上报水位。
- 招聘专员从聊天列表点击打开会话时，使用列表最近消息时间辅助标记本次快照覆盖范围；不再为列表待处理状态单独生成日志。
- 对已换到微信、且页面可见微信号或聊天文本明确出现微信账号的候选人，上报微信信息用于后续追踪。
- 图片、语音、附件等媒体不直接上报；只有页面已经转成文字或本身有可见文本说明时，才按文本消息上报。

## 3. 采集方向

当前方向从原来的“定时快照 + 列表待处理统计”收敛为“打开窗口触发快照”。

工作流：

```text
招聘专员打开聊天窗口
        ↓
content script 读取当前聊天窗口文本快照
        ↓
生成 candidate_chat.opened，并比较快照最后消息时间与本地成功上报水位
        ↓
无成功水位或快照更新于水位时，生成 candidate_chat.snapshot_captured / candidate_chat.wechat_captured
        ↓
事件进入本地队列并立即尝试上传
        ↓
服务器返回成功
        ↓
background 推进该候选人的本地上报水位
```

说明：

- “有效上报”只以服务器成功返回为准。写入本地队列、调试页显示、或上传失败重试都不能推进水位。
- 重复点开同一个候选人时，插件仍会重新尝试快照；只要该快照最后消息晚于本地成功上报水位，就继续提交上报。不能用本轮内存里的相同快照指纹阻止重试。
- 插件不自动点击聊天列表，不自动滚动历史消息，不阻止员工继续操作，也不向 BOSS 聊天列表插入可见 DOM 提示。
- 服务端和后续分析系统仍需要容忍重复快照。插件端水位只用于减少重复快照提交，不作为唯一去重依据。

## 4. 候选人标识策略

聊天页必须尽量复用候选人列表、详情和打招呼模块已有身份体系。

优先级：

1. 从聊天列表项、聊天窗口、链接或 DOM `dataset` 读取 `geekId`、`resumeId`、`lid`、`securityId` 等稳定标识。
2. 如果聊天窗口来自已经曝光或打开详情的候选人，继承内存注册表中的 `candidateId`、`stableId`、`stableIdSource`、`exposureKey` 和 `exposedEventId`。
3. 如果页面暴露 `conversationId`、`chatId`、`relationId` 等会话标识，可以记录为 `chatConversationId`，但不直接替代候选人 ID，除非真机验证证明它稳定对应候选人。
4. 如果只剩候选人姓名和沟通职位，则使用低置信短指纹兜底，并在 payload 中标注 `identityConfidence: "low"`。

兜底短指纹只用于本地提示和弱关联，不应被后端解释为跨页面永久身份。同名候选人存在串联风险，后续应继续通过真实 DOM 属性验证收敛稳定 ID 来源。

## 5. 本地有效上报水位

本地存储按候选人记录最近一次服务器确认成功的聊天快照水位。

建议结构：

```json
{
  "candidateId": "bo_candidate_...",
  "stableId": "abc123",
  "stableIdSource": "url.geekId",
  "lastReportedMessageAt": "2026-05-15T09:54:00.000+08:00",
  "lastReportedMessageFingerprint": "msg_...",
  "lastReportedAt": "2026-05-15T14:05:00.000+08:00",
  "lastSnapshotEventId": "evt_...",
  "messageCount": 5,
  "wechatAccounts": ["wxid_example"]
}
```

推进规则：

- 只在 background 上传批次成功后推进。
- 同一候选人只接受更新的 `lastReportedMessageAt`；相同时间下用最后消息指纹辅助判断。
- 上传失败时保留队列项并重试，不推进本地水位。
- 本地水位丢失不会影响事实日志上传，只会导致已打开过的聊天窗口更容易重新提交快照。

## 6. 聊天列表辅助覆盖

聊天列表不再单独生成“待处理”事件，也不再维护 popup 列表待处理统计。

当招聘专员点击可见聊天列表项时，插件会临时记录该列表项的候选人、沟通职位和最近消息时间。随后如果聊天窗口快照中的最后可见消息时间早于列表最近消息时间，快照事件会附带覆盖辅助字段，说明列表上观察到更晚的消息：

- `chat.coverageLastMessageAt`
- `chat.coverageSource: "manual_chat_list_open"`
- `chat.listObservedLastMessageAt`
- `chat.listObservedLastMessageTimeText`
- `chat.hasUncapturedListMessage: true`

这只用于描述本次快照可能覆盖到的列表最新时间，不生成额外聊天列表事件，也不改变 BOSS 页面。

聊天列表时间只处理明显属于今天的最近消息时间。

视为“明显今天”的时间文本：

- `HH:mm`
- `今天 HH:mm`
- `刚刚`
- `N分钟前`

忽略：

- `昨天`
- `周一`、`周二` 等星期表达
- `05-14`、`5月14日` 等非今天明确日期
- 无法解析或不确定的时间文本

列表项最近消息时间不会作为独立事件上报。插件不向 BOSS 页面插入 badge、overlay、属性标记或其他可见 DOM 提示，不触发点击、不阻止操作、不改变 BOSS 业务状态。

## 7. 聊天窗口快照内容

聊天快照记录当前聊天窗口已渲染文本消息。

每条文本消息建议包含：

- `messageIndex`
- `messageAt`
- `direction`: `candidate` / `recruiter` / `unknown`
- `status`: 例如 `已读`、`送达`
- `text`
- `fingerprint`

快照级字段建议包含：

- `messageCount`
- `firstMessageAt`
- `lastMessageAt`
- `lastMessageFingerprint`
- `snapshotCompleteness`: 当前第一版为 `visible_dom`
- `mayBeIncomplete`: 当无法确认历史是否全部加载时为 `true`
- `mediaSummary`: 只记录可见媒体节点数量，不记录媒体 URL 或二进制内容

图片、语音和附件处理：

- 不上传图片 URL、语音 URL、附件 URL 或二进制内容。
- 如果语音或图片已经被页面转成可见文字，则作为普通文本消息上报。
- 如果只有媒体节点，没有可见文字，只计入 `mediaSummary`。

## 8. 微信信息上报

已换微信属于明确敏感联系方式采集，范围必须收窄。

只在以下场景上报：

- 聊天窗口或候选人信息区域明确显示“已交换微信”并展示微信号。
- 聊天文本中明确出现“微信 / 微信号 / wx / wechat / vx / 加我微信”等上下文，并带有可识别账号。
- BOSS 页面提供了明确的微信字段或交换微信结果文本。

不上报：

- 普通“换微信”按钮文案本身。
- 图片中的微信号，除非页面已经 OCR 或转写成可见文本。
- 无微信上下文的随机短英文、数字串。

建议单独生成 `candidate_chat.wechat_captured` 事件，payload 包含：

- `candidate`
- `wechat.accounts`
- `wechat.source`: `chat_text` / `boss_exchange_field`
- `wechat.detectedAtMessageAt`
- `wechat.detectedAtMessageFingerprint`

## 9. 需要记录的日志

### 9.1 `candidate_chat.opened`

记录招聘专员打开某个候选人的聊天窗口。

### 9.2 `candidate_chat.snapshot_captured`

记录当前聊天窗口已加载文本消息快照。该事件应在打开或切换聊天窗口时尝试生成；如果本地没有成功上报水位，或快照最后消息时间晚于水位，则立即进入上传流程。

### 9.3 `candidate_chat.wechat_captured`

记录已换微信候选人的可见微信账号或明确交换微信事实。

### 9.4 `candidate_chat.capture_failed`

记录聊天页面无法识别、消息读取失败、候选人身份无法构造等异常。

## 10. 与手机端消息的关系

手机端消息是该模块的核心风险。

设计原则：

- 插件不假设电脑端能实时捕获全部手机端消息。
- 如果手机端消息后来同步到电脑端聊天列表，插件不会仅因列表变化生成日志。
- 员工打开会话后，插件再次采集当前窗口快照；如果打开动作来自列表项，快照可携带列表最近消息时间作为覆盖辅助字段。服务端根据候选人、消息时间、消息文本和指纹做合并。

## 11. MVP 范围

当前 MVP 需要完成：

- 打开聊天窗口后采集已渲染文本快照。
- 上传成功后推进本地有效上报水位。
- 聊天列表点击后的最近消息时间辅助覆盖标记。
- 微信账号在明确微信上下文中上报。
- 媒体节点跳过和计数。
- 相关纯函数、存储状态和后台上传成功路径测试。

暂不承诺：

- 自动滚动加载完整历史。
- 解析图片/语音中的内容。
- 判断聊天质量、员工绩效或候选人质量。
- 自动打开未读会话或自动处理列表消息。

## 12. 真机验证点

- 聊天列表项是否稳定暴露候选人 ID、会话 ID 或可用链接。
- 聊天窗口候选人 ID 是否能与列表曝光/详情事件稳定关联。
- 长历史会话是否需要手动向上滚动加载。
- 手机端新消息同步到电脑端后，列表最近时间是否稳定更新。
- “已交换微信”在真实页面中如何展示，微信号是否是 DOM 文本、辅助文本、还是图片。
- 聊天窗口是否会虚拟化消息 DOM，导致当前可见快照不完整。
