# 聊天记录模块详细设计

## 1. 模块定位

聊天记录模块用于支持后续回复速度、聊天质量和话术转化率分析。

该模块与候选人列表、详情、打招呼模块不同。聊天记录不仅发生在电脑端，也可能发生在手机端。Chrome 插件只能观察电脑端 BOSS 页面，因此聊天记录需要采用更适合补全和聚合的采集方式。

## 2. 核心目标

- 记录打开过的候选人的聊天内容或聊天快照。
- 支持后续计算候选人消息和招聘专员回复之间的时间差。
- 支持后续分析招聘专员使用的话术和候选人转化效果。
- 允许服务端接受冗余数据，由后续分析系统做合并和去重。

## 3. 采集方向

当前方向是“会话快照 + 定时上报”。

含义：

- 插件关注招聘专员打开过或进入过的候选人聊天会话。
- 对这些会话定时读取当前可见或可获取的全量聊天信息。
- 将聊天快照上报到日志系统。
- 服务端可以接受重复快照。
- 后续分析系统根据候选人、会话、消息时间和消息内容做去重与合并。

## 4. 需要记录的日志

### 4.1 聊天会话打开日志

记录招聘专员打开某个候选人的聊天会话。

### 4.2 聊天会话快照日志

记录某个候选人当前会话中的聊天信息快照。

该日志可以定时产生，也可以在打开会话、切换会话、页面即将离开时产生。

### 4.3 聊天会话关闭日志

记录招聘专员关闭或离开某个聊天会话。

### 4.4 聊天采集异常日志

记录聊天页面无法识别、消息读取失败、快照为空等情况。

## 5. 快照内容方向

聊天快照需要支持后续分析：

- 消息方向
- 消息时间
- 消息顺序
- 消息文本或脱敏文本
- 消息状态
- 候选人上下文
- 招聘专员上下文

是否采集原文、脱敏文本或仅元数据，需要结合真机验证和合规要求确定。

## 6. 与手机端消息的关系

手机端消息是该模块的核心风险。

当前设计倾向：

- 插件不假设电脑端能实时捕获全部消息。
- 插件通过定时快照尽量同步当前会话已有消息。
- 手机端发送或接收过的消息，如果后来同步到电脑端聊天记录中，可以通过后续快照补齐。
- 服务端和分析系统需要容忍重复快照和延迟补齐。

## 7. MVP 范围

聊天记录模块在 MVP 中先做验证，不直接承诺完整实现。

MVP 需要完成：

- 真机验证电脑端聊天页面能观察到哪些消息。
- 真机验证聊天列表和聊天详情是否适合做会话快照。
- 验证手机端消息是否会回流到电脑端聊天记录。
- 确定定时上报的可行性。
- 确定聊天快照是否会造成明显性能问题。

## 8. 真机验证点

- 聊天记录是否在 DOM 中完整存在。
- 历史消息是否需要滚动加载。
- 消息时间是否完整显示。
- 手机端发送的消息是否会同步到电脑端。
- 候选人新消息是否会自动出现在电脑端页面。
- 消息文本是否包含手机号、微信、地址等敏感信息。
- 大量聊天快照是否会导致日志量过大。
