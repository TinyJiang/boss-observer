# 候选人列表模块详细设计

## 1. 模块定位

候选人列表模块用于记录招聘专员在列表中实际看到过哪些候选人。

这是 MVP 的核心模块之一。列表曝光是后续分析候选人筛选漏斗的分母。如果没有候选人列表曝光日志，就无法判断招聘专员是在多少候选人中选择打开和打招呼。

## 2. 核心目标

- 记录候选人列表页面曝光。
- 记录候选人卡片在列表中出现。
- 记录候选人曝光时的职位和筛选上下文。
- 支持后续分析曝光到打开详情、曝光到打招呼的转化关系。

## 3. 需要记录的日志

### 3.1 候选人列表曝光日志

记录招聘专员进入或看到候选人列表。

用于确认当前页面处于候选人筛选工作场景。

### 3.2 候选人卡片曝光日志

记录某个候选人卡片出现在列表可见区域中。

只要候选人在列表中出现过，就应该被记录下来。

## 4. 触发时机

- 进入候选人列表页面时记录候选人列表曝光日志。
- 候选人卡片进入可见区域时记录候选人卡片曝光日志。
- 列表滚动导致新候选人进入可见区域时记录候选人卡片曝光日志。
- 筛选确认、职位切换、列表刷新后重新记录新的候选人曝光。

## 5. 曝光判定

候选人卡片曝光建议以可见区域为基础。

概要原则：

- 候选人卡片进入浏览器可见区域后视为曝光。
- 可以接受重复曝光，后续分析系统再聚合。
- 插件不判断曝光是否有效阅读。
- 插件不判断候选人是否值得打开。
- 插件第一版不保存完整候选人卡片文本，只记录可关联的候选人标识、短指纹、核心卡片字段和结构信号。

具体曝光阈值、重复曝光规则和去重策略在真机验证后确定。

## 5.1 当前实现说明

当前第一版实现包含：

- `candidate_list.list_viewed`：进入候选人列表页时记录一次列表曝光。
- `candidate_list.card_exposed`：候选人卡片出现在当前 frame 可见区域时记录一次卡片曝光。
- 支持扫描同源 iframe。当前推荐牛人页的候选人列表实际位于 `/web/frame/recommend/` frame 内。
- 同一 `pageType + url + candidate stableId` 在本次页面生命周期内只记录一次，避免滚动回原位置造成大量重复事件。

当前第一版 DOM 识别仍是保守启发式：

- 以包含“打招呼”的按钮或链接作为候选人卡片锚点。
- 向上查找有限层级祖先，并要求文本中出现年龄、薪资或“期望”等候选人卡片信号。
- TODO：继续在真实 BOSS 推荐、搜索、意向沟通页面验证 DOM 结构后，用更稳定的选择器替换文本锚点启发式。

当前第一版候选人标识策略：

- 优先从卡片 dataset 或详情链接中提取 `geekId`、`resumeId`、`lid`、`securityId` 等稳定标识。
- 如果页面没有暴露稳定标识，则使用卡片文本、详情链接和来源 URL 生成短指纹。
- 从卡片可见文本中解析 `profile` 核心快照：姓名/称呼、薪资、年龄、经验、学历、求职状态、活跃状态、期望城市、期望岗位和少量短标签。
- 不把完整卡片文本、完整优势描述、完整工作/教育经历正文写入事件 payload。
- 正式 payload 只保留候选人身份、曝光关联键、列表 URL/类型、核心 profile 和可用的 `cardIndex`；空 profile 字段、页面完整对象、识别信号、文本长度和可见比例不进入 CLS。
- 列表曝光时会给候选人卡片写入 `data-boss-observer-candidate-id`，值来自候选人稳定身份派生的 `candidateId`，不是本地递增序号；同一候选人在扩展重载后仍应生成同一个 ID。
- 内存注册表同时保存 `candidateId`、`exposureKey` 和曝光事件 ID：`candidateId` 表示候选人身份，`exposureKey` 表示某个列表页面里的某次曝光事实。
- 列表页会监听候选人卡片点击，只记录最近交互关联，不额外采集正文；如果点击发生时该卡片尚未被扫描到，会先按曝光事实补注册一次。

## 6. 依赖上下文

候选人卡片曝光日志需要尽量带上：

- 页面会话上下文
- 当前职位上下文
- 当前筛选上下文
- 当前页面类型
- 候选人可识别信息

候选人稳定标识方式在真机验证后确定。

## 7. MVP 范围

MVP 需要完成：

- 能识别候选人列表页面。（已完成第一版）
- 能记录候选人列表曝光。（已完成第一版）
- 能记录候选人卡片曝光。（已完成第一版）
- 能在滚动时持续记录新出现的候选人。
- 能把职位和筛选上下文附加到曝光日志中。（待职位和筛选模块实现后补充）

## 8. 真机验证点

- 候选人卡片 DOM 结构是否稳定。
- 候选人列表是否虚拟滚动。
- 候选人卡片是否会复用 DOM 节点。
- 候选人是否有稳定链接或标识。
- 卡片曝光是否会因为懒加载产生误判。
- 列表刷新后是否会出现相同候选人重复展示。
