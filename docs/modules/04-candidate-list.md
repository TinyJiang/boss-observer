# 候选人列表模块详细设计

## 1. 模块定位

候选人列表模块用于记录招聘专员在列表中实际看到过哪些候选人。

这是 MVP 的核心模块之一。列表曝光是后续分析候选人筛选漏斗的分母。如果没有候选人列表曝光日志，就无法判断招聘专员是在多少候选人中选择打开和打招呼。

## 2. 核心目标

- 记录候选人列表页面曝光。
- 记录候选人卡片在列表中出现。
- 记录候选人曝光时的职位和筛选上下文。
- 支持后续分析曝光到打开详情、曝光到打招呼的转化关系。

## 3. 需要记录的日志

### 3.1 候选人列表曝光日志

记录招聘专员进入或看到候选人列表。

用于确认当前页面处于候选人筛选工作场景。

### 3.2 候选人卡片曝光日志

记录某个候选人卡片出现在列表可见区域中。

只要候选人在列表中出现过，就应该被记录下来。

## 4. 触发时机

- 进入候选人列表页面时记录候选人列表曝光日志。
- 候选人卡片进入可见区域时记录候选人卡片曝光日志。
- 列表滚动导致新候选人进入可见区域时记录候选人卡片曝光日志。
- 筛选确认、职位切换、列表刷新后重新记录新的候选人曝光。

## 5. 曝光判定

候选人卡片曝光建议以可见区域为基础。

概要原则：

- 候选人卡片进入浏览器可见区域后视为曝光。
- 可以接受重复曝光，后续分析系统再聚合。
- 插件不判断曝光是否有效阅读。
- 插件不判断候选人是否值得打开。

具体曝光阈值、重复曝光规则和去重策略在真机验证后确定。

## 6. 依赖上下文

候选人卡片曝光日志需要尽量带上：

- 页面会话上下文
- 当前职位上下文
- 当前筛选上下文
- 当前页面类型
- 候选人可识别信息

候选人稳定标识方式在真机验证后确定。

## 7. MVP 范围

MVP 需要完成：

- 能识别候选人列表页面。
- 能记录候选人列表曝光。
- 能记录候选人卡片曝光。
- 能在滚动时持续记录新出现的候选人。
- 能把职位和筛选上下文附加到曝光日志中。

## 8. 真机验证点

- 候选人卡片 DOM 结构是否稳定。
- 候选人列表是否虚拟滚动。
- 候选人卡片是否会复用 DOM 节点。
- 候选人是否有稳定链接或标识。
- 卡片曝光是否会因为懒加载产生误判。
- 列表刷新后是否会出现相同候选人重复展示。
